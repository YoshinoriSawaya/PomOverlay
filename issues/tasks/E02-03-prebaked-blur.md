# E02-03: ぼかしの事前ベイク

親: [E02: パフォーマンス改善](../epics/E02-performance.md)

## 概要

毎フレーム `BlurEffect`(ソフトウェア実装)をかけるのをやめる。帯幅が決まったあとに、ぼかし半径×線の太さの組み合わせをあらかじめ `RenderTargetBitmap` で描いておき、`OpacityMask` として使う。色・不透明度・流れは、今までどおりグラデーションブラシ側で毎フレーム処理する。

## 完了条件

- 毎フレームの `BlurEffect` が無くなっている
- 見た目が今と大きく変わらない(手動確認)
- E02-01 の手順で計測して、改善前より負荷が下がっている

## 依存関係

E02-02 の後(帯幅が決まっている必要がある)。

## 設計の決定

- 一度実装してから、効果が無いことが分かったので破棄した(コミットしていない)
- 実装した方式:ぼかした枠線の濃さを式で計算し(辺は端からの距離の1次元関数、角は縦横に分離したガウスぼかしの積の差)、0.5px 刻みで丸めたマスク画像をキャッシュして `OpacityMask` に使う。1モニターを角4つ・辺4つの部品で描き、色のグラデーションブラシはモニター座標で共有する
- `BlurEffect` の Radius とガウス分布の標準偏差の対応は σ = Radius / 3 で合っていた(見た目の比較で確認)

## 検証結果

2026-09-29

- 見た目:黒背景の上で旧版と比べ、差は255段階で平均0.2以下・最大2。見た目は一致した
- 負荷:CPU は変わらなかった(Rest で 48〜53%、E02-02 は 49%)
- 原因を切り分けるため、実験用ビルドで条件を変えて計測した(Rest 固定、1コア換算)

| 実験 | PomOverlay CPU | DWM CPU |
|------|------:|------:|
| そのまま | 51% | 21% |
| デバッグ表示なし | 34% | 20% |
| 30FPS(タイマー33ms) | 29% | 16% |
| 最初の数フレーム以降は描画を更新しない | 1% | 5% |

- デバッグ表示なし・30FPS で、`BlurEffect` 版(E02-02)と事前ベイク版を比べた

| 条件 | CPU | GPU | DWM CPU | WorkingSet / Private |
|------|------:|------:|------:|------:|
| `BlurEffect` / Rest | 18.7% | 15.0% | 15.5% | 152 / 307 MB |
| 事前ベイク / Rest | 16.4% | 7.6% | 14.9% | 157 / 215 MB |
| `BlurEffect` / Focus | 17.9% | 8.0% | 14.8% | 152 / 281 MB |
| 事前ベイク / Focus | 20.3% | 10.3% | 16.6% | 152 / 192 MB |

- 分かったこと
  - 負荷のほぼすべては、毎フレームのレイヤードウィンドウの再描画と転送。ピクセル数(帯の面積)とフレームレートに比例する。`BlurEffect` の計算は主因ではなかった
  - デバッグ表示(初期状態でスクリーン1に出ている)だけで約17%を使っている
  - Focus(線2px + ぼかし10px)でも Rest と同じ負荷。帯幅が全モードの最大(手元の設定で132px)で固定されているため
- 事前ベイクは CPU・WorkingSet に効果が無く、約300行の複雑さに見合わないので破棄した(ユーザー判断)。代わりに E02-04〜06 を起こした

## 未検証のまま残したこと

- 帯幅を小さくした後(E02-06)に、`BlurEffect` の計算コストが目立ってくるかどうか。その場合はこのタスクの方式を再検討する
