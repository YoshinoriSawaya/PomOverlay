# E02-07: 帯の面積によらない固定費の切り分け

親: [E02: パフォーマンス改善](../epics/E02-performance.md)

## 概要

E02-06 で Focus の帯幅を132px → 14px(面積約1/9)にしたが、CPU は約29% → 約20% までしか下がらなかった。帯の面積によらない固定費の内訳を調べ、さらに削るべきかを判断する。

## 完了条件

- 固定費の主な内訳が数値で分かっている
- さらに対策するかどうかの判断が記録されている

## 依存関係

E02-06 の後。

## 設計の決定

- 実験用ビルド(環境変数で条件を切り替え、コミットしない)を Focus 固定・30FPS・20秒で計測した
- 結論:ここで打ち切る。固定費の大半はウィンドウ枚数(1枚あたり約2ポイント)で、四辺を覆うには長方形のウィンドウが4枚要る。1枚にまとめると全画面に戻り、面積のコストが復活する。残りの約17〜20%(1コア換算)は PC 全体(16スレッド)では約1.2%で、これ以上は費用対効果が低い
- さらに軽くしたい場合は、`config.json` の `Fps` を下げれば負荷はほぼ比例して下がる(例:15FPS)

## 検証結果

2026-09-29、Focus 固定(帯幅14px)、1コア換算。計測ごとに数%のぶれがある

| 実験 | PomOverlay CPU | DWM CPU |
|------|------:|------:|
| A そのまま | 17.3% | 12.5% |
| B デバッグ表示なし | 20.1% | 15.3% |
| C `BlurEffect` なし | 15.4% | 16.0% |
| D 帯ウィンドウを1モニターあたり上の1枚だけ | 10.5% | 9.5% |
| B + C | 12.1% | 17.2% |
| B + C + D | 5.5% | 9.5% |

- ウィンドウ枚数:4枚 → 1枚で約7ポイント減(1枚あたり約2ポイント)。2モニター × 4枚 = 8枚を毎秒30回描いて転送している
- `BlurEffect`:約2〜5ポイント
- デバッグ表示:E02-04 以降はほぼ0(ぶれの範囲)

## 未検証のまま残したこと

- ウィンドウ1枚あたりのコストが WPF の描画パイプライン側か、`UpdateLayeredWindow` による転送側かは切り分けていない
- 帯ウィンドウの中身をモニター全体サイズの `Rectangle` ではなく帯の大きさの要素にした場合の差は試していない

## ステータス

完了(2026-09-29)。これ以上の対策はしない判断
